# Prior art for deployd — what exists, and what it tells us we missed

**Status: research, 2026-09-05.** Compares the deployd design
(`docs/superpowers/specs/2026-09-05-deployd-design.md`) and its implementation plan
against tools that already solve build-on-push, and lists what those tools know that
the design does not yet account for.

Findings are marked:

- **Defect** — the documents as written would produce wrong behaviour. Two of these,
  both reproduced.
- **Gap** — a problem every comparable tool has hit and deployd has no answer for.
- **Decide** — a choice deployd made by omission that the prior art makes deliberately.
- **Validated** — a deployd decision the prior art confirms is the right one.

## 1 · The landscape

Four tiers do this job. deployd sits between the first and the third, which is an
unoccupied and sensible place to be.

| Tier | Examples | Trigger | Unit of deploy | Size |
|---|---|---|---|---|
| Generic hook runner | [adnanh/webhook](https://github.com/adnanh/webhook), [Git-Auto-Deploy](https://github.com/olipo186/Git-Auto-Deploy) | Webhook | A shell command | One binary / one Python service |
| Release-directory deployer | [Capistrano](https://capistranorb.com/documentation/getting-started/structure/), Ansistrano, [Deployer](https://deployer.org/) | Run from a laptop | `releases/<ts>` + `current` symlink | A framework |
| Tiny PaaS | [piku](https://github.com/piku/piku), [dokku](https://dokku.com/) | `git push` to the server | An app with a Procfile | 250 lines of bash → a plugin system |
| Self-hosted platform | [Coolify](https://coolify.io/docs/), CapRover, Dokploy, [Kamal](https://kamal-deploy.org/) | GitHub App webhook | A container | A Laravel app / a Ruby gem |
| Hosted reference | [Render](https://render.com), [Cloudflare Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/build-watch-paths/) | Webhook | A service | — |

deployd takes the webhook trigger from tier 4, the `releases/` + `current` structure
from tier 2, the "one small thing, no dependencies" posture from tier 1, and skips
containers entirely. Nothing in tier 1 has a queue, a rollback, or a release history.
Nothing in tiers 2–4 is one file of Node with no npm dependencies.

### The trigger, compared

piku and dokku use `git push` to a server-side remote. That needs no webhook, no
shared secret, no inbound TLS, and it cannot be missed — the push either lands or
the developer sees it fail. The cost is that a deploy originates on a laptop, so
"what is on `main`" and "what is deployed" drift silently.

deployd's webhook is the right choice for the stated goal of mirroring Render, and
`deployd run <name>` over SSH is already the piku-shaped escape hatch. Worth knowing
that the alternative exists and is cheaper, in case the webhook path turns out to be
the thing that keeps breaking.

## 2 · Defects — reproduced

### D1 · The spec's fetch leaves the built commit unreachable, and git will delete it

Section 4, step 1 says: "`git fetch origin <BRANCH>` in the bare clone … The branch
head sha is read from the fetch output."

`git clone --bare` does not create a `remote.origin.fetch` refspec. Git's own
documentation states that with `--bare`, "neither remote-tracking branches nor the
related configuration variables are created". So `git fetch origin main` in that
clone writes **only** `FETCH_HEAD`. `refs/heads/main` in the bare clone stays at the
sha the clone was made with, forever, and the newly fetched commit is reachable from
no ref at all.

Reproduced on git 2.43.1:

```
$ git clone --bare file://…/origin bare && cd bare
$ git config --get-all remote.origin.fetch
(none)
$ git fetch origin main
 * branch            main       -> FETCH_HEAD
$ git for-each-ref
9bf7ed9… commit  refs/heads/main        # still the OLD sha
$ git rev-list --all | grep 9a8a24c
                                        # the new commit: not reachable from any ref
$ git prune --expire=now
$ git rev-parse --verify 9a8a24c^{commit}
fatal: Needed a single revision                # deleted
```

A live worktree does protect its own commit — I confirmed that too. But deployd's own
step 7 removes release worktrees, and git runs `gc --auto` on its own after enough
loose objects accumulate. So the failure is delayed rather than avoided: the objects
survive while a release directory holds them and become deletable the moment prune
removes it. Two further consequences even before any gc: every fetch redownloads
everything, because nothing local ever advances; and `git diff --name-only
<live-sha>..<sha>` in step 2 depends on both commits still being present.

**The implementation plan already gets this right.** Task 7 defines `fetchBranch` as
fetching `+refs/heads/${branch}:refs/heads/${branch}`, which creates a real ref.
Verified that this version survives `git prune --expire=now` and that the two-dot diff
still works.

**Action:** correct the spec text so the two documents agree. Anyone implementing from
the spec alone writes the broken version. The spec should say: fetch with an explicit
refspec into a local ref, and read the sha with `git rev-parse` on that ref rather
than by parsing fetch output — fetch's output format is not a stable interface.

### D2 · The 1 MiB body cap will silently drop real pushes

The design caps the request body at 1 MiB and answers 413 before checking the
signature; the plan implements exactly that (`MAX_BODY = 1024 * 1024`).

GitHub's documented limits are different: **payloads are capped at 25 MB**, and a push
event's `commits` array carries **up to 2048 commits**. A merge of a long-lived
branch, a vendored-dependency commit, or a squash of a large history produces a push
payload well past 1 MiB.

What happens then is the bad part. deployd returns 413. GitHub marks the delivery
failed and **does not retry** — that is documented behaviour, not an accident. deployd
has no polling fallback by design. So the push is simply never deployed, and nothing
on the box says so; the only trace is in GitHub's delivery log and one journald line.

Because the payload is a doorbell and only two fields are read, the fix is free: raise
the cap to 25 MiB, keep the streaming abort above it. A 25 MiB buffer once per
delivery on a box that is about to run `npm ci` is not the constraint.

## 3 · Gaps the prior art fills

### G1 · Missed deliveries are recoverable, and the spec assumes they are not

The non-goals say a push arriving while the service is down is lost, and recovery is
`deployd run` plus the `deployd check` habit. The first half is right — GitHub does
not retry. The second half gives up too early. GitHub keeps **three days of delivery
history** and exposes list-deliveries and redeliver REST endpoints; its docs carry a
worked recipe for automatically redelivering failed deliveries.

deployd cannot use those endpoints without a token, which contradicts the
deploy-key-only decision. But it already has the cheaper half of the answer and does
not exploit it: `deployd check` runs `git ls-remote` and prints the branch head beside
the live sha. Two small changes close the whole class of missed deploys:

1. Make `check` **exit non-zero when behind**, so a cron entry or the box's health
   watch turns a lost webhook into an alert with no new code.
2. Optionally, a per-repo `POLL=<seconds>`: `ls-remote`, and queue a run when the head
   differs from live. Roughly fifteen lines, no dependency, and it makes the box
   survive its own downtime, a GitHub incident, and D2 above.

Every hosted tool has this same hole. The difference is that they have a builds screen
that shows you nothing built. deployd has no UI, so the silent version is worse.

### G2 · Nothing tells anyone a deploy failed

There is no notification of any kind — not email, not a command hook, nothing beyond
journald and a log file. Every comparable tool has one: Deployer ships a Slack recipe,
ArgoCD and Octopus have notification subsystems, GitHub Actions has `failure()`.

This matters more for deployd than for them, because of a deliberate design choice:
after a failed DEPLOY, `pending` stays set and **webhook-triggered runs are refused
until someone intervenes**. That is the right call, but it converts an unnoticed
failure into an unnoticed and *sticky* failure. Pushes then pile up doing nothing,
and the only signal is a capitalised word in `deployd status`, which nobody is
watching.

Minimal fix in keeping with the no-dependency rule: one config key, `ON_FAILURE`, run
through `sh -c` with `DEPLOY_NAME`, `DEPLOY_SHA`, the outcome, and the log path in its
environment. The user writes their own `curl` or `mail` line. That is a handful of
lines and it keeps deployd out of the notification business entirely.

### G3 · No shared directory between releases — Capistrano's oldest lesson

Capistrano has `shared/` with `linked_dirs` and `linked_files`, and symlinks them into
each release, for one reason: a release directory is thrown away. deployd gives each
build a fresh worktree and nothing that survives it.

Two consequences. Anything the deployed app writes inside its own directory — uploads,
a SQLite file, generated caches — is destroyed by the next deploy, or silently
reverted by a rollback to an older directory. And `.env`-style files that are not in
git have nowhere to live.

For the aliasroute pattern this never bites, because DEPLOY copies out to `/opt` and
the app runs from there. For anything running directly from `current`, it will bite,
and it will bite as data loss rather than as a failed build. At minimum this belongs
in the spec as a stated rule: *nothing in a release directory survives; persistent
state lives outside it*. A `LINK=` key is the eventual Capistrano-shaped answer if it
turns out to be needed.

### G4 · Every build is a cold `npm ci`

A fresh worktree per release means the package manager starts from nothing every push.
The settled CI advice is precise about the fix: do **not** carry `node_modules`
between builds — `npm ci` deletes it anyway, and restored native modules break across
Node versions — but **do** persist the package manager's download cache.

One line in the environment table does it: point `npm_config_cache` (and
`XDG_CACHE_HOME`) at `/var/lib/deployd/<name>/cache/`, a per-repo directory that step
7's prune never touches. On a small box this is minutes per deploy. It is an addition
to the deliberately-small environment table, not a leak of the ambient environment, so
it does not weaken that decision.

### G5 · Branch deletes will produce recurring noise

`git push --delete` on the watched branch sends a push event whose `ref` is the
watched branch, with `deleted: true` and an all-zeros `after`. deployd matches it on
ref and `ssh_url`, queues a run, and the fetch fails because the branch is gone. The
result is a `fetch failed` outcome and an alarming log entry for something entirely
routine. One line in the hook handler: ignore payloads with `deleted === true`.

### G6 · Matching on `repository.ssh_url` fails quietly on rename

A repository rename or transfer changes `ssh_url`. Git over SSH follows GitHub's
redirect, so fetches keep working, but the webhook payload carries the **new** name
and no longer equals the `REPO` in the config. deployd answers `200 ignored` and stops
deploying, with no error anywhere.

The design already shows this instinct on the other side of the problem — `HOOK_HOST`
exists so `status` notices a renamed *box*. The repo side deserves the same care.
Cheapest robust version: match `ssh_url` **or** the `owner/repo` derived from `REPO`
against `repository.full_name`, and write every ignored push to journald with the
`ssh_url` it carried, so the failure is greppable rather than invisible.

### G7 · Secrets are recoverable from run logs, and deployd knows the values

The design states plainly that it cannot stop a BUILD from echoing a secret. That is
honest, and it is also more pessimistic than necessary. GitHub Actions solves the same
problem with `::add-mask::`: it knows the secret values, so it replaces them in log
output. deployd knows exactly the values it injected from the two env files.

Replacing those values with `***` in the run-log writer covers the common accident —
`set -x`, a stray `env`, a failing `curl` printing its `Authorization` header. It is
about ten lines in `lib/log.mjs`, applied per chunk as it is written. Two cautions
from the Actions experience: skip short or low-entropy values, since masking `true` or
a two-character token corrupts the log for no gain; and masking is best-effort, so the
existing honest sentence stays in the docs.

## 4 · Decisions made by omission

### C1 · One worker for the whole box is stricter than anything comparable

Kamal locks per application. Coolify queues per application. dokku and piku serialise
per app. deployd serialises across every repository on the box, so one twenty-minute
build blocks a one-line fix to an unrelated site.

The queue is already keyed by name, and every invariant in the design — dedup,
run-again-after, `pending` — is already per-name. A map of name → worker is a
contained change. The argument for keeping one worker is real (CPU and RAM on a small
box, and two concurrent `npm ci` runs are genuinely unpleasant), but it should be
written down as the reason, because right now the constraint reads as an accident.

### C2 · No commit-status feedback, and it should be a stated non-goal

Coolify posts `pending` then `success`/`failure` back to the commit, so a push shows
its deploy state in GitHub. deployd cannot: it has a deploy key and no API token, by
an explicit decision. That is fine, but it is currently unstated, so it reads as
something nobody thought of. Add it to the non-goals with the reason, and point at
`ON_FAILURE` from G2 as the substitute.

### C3 · Path filters — the semantics match Cloudflare's, with one valve missing

Cloudflare evaluates excludes first, then includes, which is exactly deployd's
`IGNORE` then `WATCH`. Render and Railway are the same mechanism with different
syntax. Good company.

deployd is in fact **better** than the hosted tools on one point: it diffs against the
*live* sha, so a change under a watched path is never lost by being skipped once, and
the two-dot diff means a force-push or rebase does not confuse it. The hosted tools
diff against the previous build of the branch and do lose changes this way. Keep it.

The one thing worth copying: Cloudflare **bypasses path matching entirely** for pushes
with zero file changes, 3000+ changed files, or 20+ commits. The zero-change case is
the notable one — an empty commit is a common way to force a redeploy, and deployd
would skip it. A large-changeset escape hatch is a cheap safety valve for the case
where the diff is too big to reason about.

## 5 · Validated — decisions the prior art confirms

- **The doorbell property.** Reading only "which repo, which branch" from the payload
  and taking the sha from deployd's own fetch is stronger than the tier deployd
  otherwise sits in. adnanh/webhook passes payload fields straight into commands;
  Git-Auto-Deploy runs `git pull` on the strength of a request. deployd behaves like
  Coolify here, which is the right end of the range.
- **Two ids, attempt and release.** Nothing in tier 1 or tier 2 does this. It is
  precisely the fix for Capistrano's failure mode where a second build of the same
  commit overwrites the directory that `current` points at.
- **A serialised queue with dedup and run-again-after.** adnanh/webhook has no queue
  at all and will happily run overlapping deploys on a burst of pushes;
  Git-Auto-Deploy documents no locking. This is deployd's clearest advantage over the
  tools it most resembles.
- **Rollback target resolved at accept time and protected from prune.** The correct
  directory-model equivalent of Kamal's "the old container is still sitting there".
- **Refusing webhook runs while `pending` is set.** Stricter than Kamal, which leaves
  the old container serving and just reports a failure. deployd has no proxy and no
  health gate, so being loud is the right substitute for being safe.
- **Answering the webhook 202 immediately and running asynchronously.** GitHub's
  timeout is 10 seconds and the documented best practice is to verify, enqueue, and
  return at once. deployd does exactly this.
- **Building into a git worktree rather than copying.** Capistrano's structure with
  cheaper disk, since worktrees share one object database.

## 6 · Recommended order

**Fix before implementing**

1. D1 — correct the spec's fetch step to use an explicit refspec and `rev-parse`. The
   plan is already right; the spec is the trap.
2. D2 — raise the body cap to 25 MiB to match GitHub's documented limit.

**Cheap, high value, in keeping with the design**

3. G5 — ignore `deleted: true` pushes. One line.
4. G2 — `ON_FAILURE` command hook. A failed deploy is currently silent *and* sticky.
5. G4 — point the package-manager cache at a per-repo directory prune never touches.
6. G7 — mask known env-file values in run logs.
7. G1 — make `deployd check` exit non-zero when behind, so a cron turns a lost webhook
   into an alert.

**Decide deliberately and write down the reason**

8. C1 — one worker per box, or per repo.
9. G3 — state that nothing in a release directory survives, or add `LINK=`.
10. G6 — match on `full_name` as well as `ssh_url`, and log ignored pushes.
11. C2, C3 — record the commit-status non-goal; consider the zero-change escape hatch.

## 7 · One documentation correction

The config table describes `KEY` as a way to "share one machine-user key across
repos", which is correct. The decisions table at the top of the spec describes the
same thing as "an optional shared key", and `deployd add` always prints
`gh repo deploy-key add`. GitHub is strict here: a key can be attached to exactly one
repository, and a second attempt fails with "Key is already in use"; the documented
workaround is a machine user account, whose SSH key reaches every repo it can see.

So the shared-key path is not a shared *deploy* key and cannot be — it is a machine
user's key, and `add` printing the deploy-key command in that case sends the operator
straight into the error. Make `add` detect a configured shared `KEY` and print the
machine-user instruction instead, and state the one-repo-per-deploy-key constraint in
the config table where someone will read it.
